# SARA — instructions for continuing agents

1. **Read [SARA_PROJECT_STATUS.md](SARA_PROJECT_STATUS.md) first.** It holds the current user requirements, implementation/evidence ledger and prioritized unfinished work. Then read [SARA_PROJECT_CONTEXT.md](SARA_PROJECT_CONTEXT.md) for technical decisions and [SARA_SETUP_GUIDE.md](SARA_SETUP_GUIDE.md) for run/test commands. Inspect actual files and `git status` before trusting earlier claims.
2. The latest UI direction supports multiple live dashboard looks: Jarvis rings, warm companion, playful cartoon buddy, Aurora and minimal Focus, with daily/idle rotation and saved manual choice. Use procedural canvas and CSS; do not substitute static screenshots or reference video. Preserve clear conversation and controls across looks, with speech motion driven by actual playback and reduced-motion support.
3. Preserve the modular backend/frontend architecture. Prefer local/free components where practical. Make capability claims match current scope and real tool results. Explain changes to the user in plain Hindi/English mix.
4. Keep personal data local and reviewable. The latest user direction authorizes a persisted **Trusted routines** mode: skip repeated review only for the bounded routine types/payloads in `policy.py`; recheck that grant and Stop before execution. Keep exact-content review for sends, deletes, writes, sensitive changes, focused-window input and custom executables. Preserve session isolation, stale-action rejection and truthful partial failures. Screen/camera capture starts only from explicit UI controls and browser permission. Snapshots reach the local vision model through a sent message or a separately enabled periodic visual check-in while sharing remains active; Stop must end that access. Use only approved long-term memories. Do not introduce unrestricted shell/admin access, silent capture, model self-modification or silent personal-fact persistence.
5. Preserve existing staged/uncommitted work and user data. Do not commit keys, `.env`, `.venv`, private `sara_data/`, recovery backups or activity logs. Do not overwrite malformed local data without preserving its original bytes.
6. Run meaningful verification appropriate to the change. Use `tests/run_offline.py` and browser `fixture` mode for isolated checks. Mock checks do not prove physical speech, visible Windows app outcomes, live notifications or external account integration; state those limits.
7. **Update SARA_PROJECT_STATUS.md after meaningful changes**: target/implementation/evidence/remaining work, exact verification date/result, and next-chat handoff. Keep planned, implemented, verified and physically unverified states distinct. Do not mark the full Jarvis vision complete from partial progress or test counts alone.

If a new chat is outside the SARA checkout, ask it to open the actual project or provide the status-file path; these instructions are discoverable only when the repository is available to that chat.
